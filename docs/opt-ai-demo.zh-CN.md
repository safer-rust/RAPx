# opt 展示：建议占 2 页

以下两页可插入团队总稿，在 12 页总篇幅中展示 opt 的证据、AI 复核和验证流程。

## 第 1 页：让优化候选带着证据进入 AI 复核

主图：`Rust 源码 → RAPx opt → 结构化候选 → AI 复核 → 原证据 + 建议 + 验证计划`。

只展示三个要点：

1. Rust 静态分析定位候选，输出函数源码、准确位置、静态证据。
2. AI 给出保留/疑似误报/证据不足，解释原因并提出优化和验证建议。
3. 原告警留档，AI 不替代安全证明；异常和离线状态显式标记。

讲稿（约 45 秒）：

“我负责 opt，目标是把优化提示变成开发者能检查的建议。RAPx 先完成原有的静态
分析，再把候选和源码上下文导出。新增的 opt-ai 命令让模型逐条复核并生成报告。
报告同时保留静态判断和 AI 意见，因此模型说‘疑似误报’也不会抹掉原来的证据。
没有 key 时可以先离线导出，再由助手按配套 skill 复核。”

页面底部放 `cargo rapx opt-ai` 一行命令和一条报告截图即可。不要逐条介绍六类规则。

## 第 2 页：一个可以重跑的安全优化案例

左右各放一行核心代码：

```rust
// 前：反复删除 Vec 第一个元素，使剩余元素前移
output.push_str(&parts.remove(0));
// 后：FIFO 容器从头部取出，保持片段顺序
while let Some(part) = queue.pop_front() {
    output.push_str(&part);
}
```

中间用三步箭头：`候选与原因 → 安全重写 → 正确性测试 + 再跑 opt`。
对照表只写本次演示实测数据：

| 项目 | 修改前 | 修改后 |
|---|---|---|
| Vec 首部删除候选 | 脚本断言为 1 | 脚本断言为 0 |
| 与 concat 参考结果一致 | 运行测试确认 | 运行测试确认 |
| 覆盖输入 | 343 组短串组合 + 空输入 + 1000 段增长 | 同一组 |
| 性能收益 | 未在此演示测量 | 不填写提速倍数 |

最终应附 `demo_opt_ai.py` 实际产出的 `result.json`，而不是仅凭上表认定跑过。
示例补丁是预先手工编写、feature 选择的两种实现；不要称为“模型自动修复成功”。
若要展示真实 AI 复核，使用团队服务执行脚本 `--api` 并截图真实结果；mock 不能冒充。

讲稿（约 50 秒）：

“这个例子将片段按队列顺序拼接，每次从 Vec 头部删除会搬移剩余元素。opt
定位到这个模式，复核时要检查调用方是否依赖连续存储、索引或其他 Vec 行为。
这个局部 FIFO 场景可以使用 VecDeque。我们用相同输入验证修改前后结果，再跑 opt 确认
该候选消失。测试通过和告警消失分别提供有限证据，实际提速仍需 release 基准。
这次新增的是证据导出、复核和报告流程，原有候选规则不是本轮的新贡献。”

演示命令（从仓库根目录）：

```bash
python3 tools/opt/demo_opt_ai.py --cargo-rapx "$PWD/target/debug/cargo-rapx"
```

原始 opt 文案中的建议与模型意见分别保留。复核应纠正不准确的 API 名称，并依据
具体用途判断建议是否适用；看到一次 remove(0) 并不能证明更换容器就一定更快。
